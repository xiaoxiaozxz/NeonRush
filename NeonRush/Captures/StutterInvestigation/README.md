# 正常行驶卡顿调查与修复 — 2026-10-21

用户反馈：正常直行、无碰撞或漂移时，约每 5 秒出现一次严重掉帧。本次使用 RTX 2070、1920×1080 Unity 编辑器 Game View，真实车辆动力学连续跑圈，未使用漂移/氮气输入；保持现有画质、跟随镜头、物理步长和车辆参数。

## 已捕获的原因

1. **动态字体生成的瞬时卡帧**。`baseline-fast-cpu-trace.json` 的约 12.70 秒处，主线程一帧为 61.85 ms，HUD 为 57.29 ms。调用链包含 `GUIStyle.GetMeshInfo → TextGenerator.GenerateText`（41.01 ms），其中 `FontAsset.UpdateGlyphAdjustmentRecords → FontEngine.GetPairAdjustmentRecords` 约 30.60 ms。动态数字、计时、检查点提示与多字号中文界面会触发文字生成及字体数据更新。
2. **驾驶 HUD 的持续重复工作**。旧小地图每次重绘重新采样 256 次路线并绘制 128 条线段，同时多次改变 GUI 矩阵；Layout/鼠标事件也走完整 HUD 绘制。文字每次 GUI 事件重新格式化。首轮 HUD 平均约 2.35 ms。
3. **诊断录制的额外开销，单独区分**。完整 CPU Profiler 录制在修复前的采样中带来约 6–8 秒间隔的 `Profiler.IntegrateSessionData / AddFrameDataAndTransferOwnership` 峰值，单帧约 162–218 ms。这一项由诊断录制触发，不能当作用户原始问题的唯一原因；最终游玩验证关闭了完整录制。第一次 38 秒轻量跑圈也未复现严重停顿，因此不声称每次运行均能稳定复现同一条卡顿链。

## 修复

- 菜单/首次显示阶段预热实际 HUD 字符、数字、字号和字形，避免行驶过程中首次生成常用字体数据。
- 小地图路线烘焙为一张 512×448 透明缓存纹理，将静态路线的 128 次绘制改为一次；检查点坐标缓存，车辆朝向和进度继续动态更新。更换路线后重建缓存。
- 非交互驾驶 HUD 仅处理 Repaint，菜单仍接收完整鼠标事件。
- 数字与记录文本以 20 Hz 更新，并在模式、检查点、氮气库存、救援状态变化时立即刷新。实际物理、计圈时间、喷射窗口、集气条与驾驶输入保持原更新频率。
- 增加 `NeonRush.HudDraw` Profiler 标记和显式编辑器测量工具 `StutterInvestigation.Start`；默认不启用完整 CPU 录制，也不在正常游戏启动时自动运行。

最后一轮没有超过 33.33 ms 的帧，0 次救援。完整 CPU 采样和轻量采样的开销不同，运行长度及车速也不同，表格不将所有平均值视为严格同条件基准；重点是捕获的实际字体阻塞、HUD 开销下降，以及修复后连续采样没有再出现严重卡帧。

全局 `GC.Alloc`（含编辑器分配）从首轮约 77.9 KB/帧降至最终约 12.3 KB/帧。此 Unity Mono 环境的 `GC.GetAllocatedBytesForCurrentThread()` 对已知测试分配也返回 0，因此早期 JSON 的 HUD 精确分配计数 0 **不可解释为零分配**，后续标记为 -1。

`baseline-no-hud.json` 是关闭 HUD 的隔离运行。其中一次 433.9 ms 峰值出现在末段；它不是本次字体根因的依据，运行中的实时调试调用也可能干扰此类采样。最终 60 秒验证期间不发送实时检查命令。

原始逐帧数据在同目录 JSON 中；`cached-hud-review.png` 是修复后实际界面，小地图方向、检查点及玩家位置显示正常。完整玩法回归见 `regression-results.json`。
